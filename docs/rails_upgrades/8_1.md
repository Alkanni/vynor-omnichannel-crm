# Production migration guide: Rails 8.1.4.1

This checkpoint upgrades the fork from Rails 8.0.5.2 to Rails 8.1.4.1 (#130, ported from chatwoot/chatwoot#15152 for CE). It keeps `config.load_defaults 7.0`, the Sidekiq/Redis setup, and every persisted serializer and encryption setting from the Rails 8.0 release. There is no database migration or data rewrite.

Rails 8.1 security support runs until **October 10, 2027**. Deploy this release only on top of the Rails 8.0.5.2 checkpoint (#129).

## Application-level changes

- Rails and every Rails component move from 8.0.5.2 to 8.1.4.1, and Action Text now pulls in the `action_text-trix` gem.
- `acts-as-taggable-on` moves to 13.0.0, because version 12 excludes Active Record 8.1. Label and tag tables, stored values, and API payloads do not change.
- `devise-two-factor` moves to 6.4.1 and `devise_token_auth` to 1.3.0, because their previous releases exclude Rails 8.1.
- `devise_token_auth` 1.3.0 forces Devise's `devise_will_save_change_to_email?` to `false`. That would apply an email change immediately without reconfirmation, and it would also turn off the `:validatable` email uniqueness and format checks. `User#devise_will_save_change_to_email?` delegates to Active Record instead, which keeps the Rails 8.0 behavior: the current email stays until the new address is confirmed, and a duplicate email is rejected with a validation error.
- `omniauth-rails_csrf_protection` moves to 2.0.1, which drops its use of the deprecated `ActiveSupport::Configurable`. The OmniAuth routes do not change.
- Bullet moves to 8.3.1 (development and test only), because 8.0.7 does not recognize Active Record 8.1.
- Rails 8.1 always makes `to_time` keep the receiver's timezone, so the deprecated `config.active_support.to_time_preserves_timezone` setting is removed. The Rails 8.0 checkpoint had already opted into this behavior.
- `db/schema.rb` uses the `ActiveRecord::Schema[8.1]` header and the Rails 8.1 dump order for extensions, indexes, and partial-index conditions. The schema version is unchanged, and a database loaded from it is identical to one loaded by Rails 8.0.
- The mailer route replacement from Rails 8.0 stays, and `app_account_path` and `app_account_conversation_path` are unchanged.

## Request behavior to audit

Rails 8.1 removes two deprecated query-string behaviors:

- A leading bracket stays part of a parameter name. For example, `[filter]=open` no longer becomes `filter=open`.
- A semicolon is no longer a query-string separator. For example, `status=open;page=2` is one `status` value, not two parameters.

The fork has no application code that relies on either behavior, but an old API client, OAuth provider, or webhook sender could still send such a query. Rails 8.1 also renders a `nil` query value as a bare key (`token`) instead of an empty assignment (`token=`). The confirmation email always carries a real token, so its link does not change.

`request.remote_ip` now reads the RFC 7239 `Forwarded` header before `X-Forwarded-For`, as Rack's `request.ip`, which the Rack::Attack throttles key on, already did. The fork uses `remote_ip` for the Rack::Attack safelist (`RACK_ATTACK_ALLOWED_IPS` plus loopback), user session tracking, the widget contact's `created_at_ip`, and Lograge. Rails 8.1.4.1 fixes the spoofing hole this opened in 8.1.0 ([GHSA-2gff-2mmg-m73p](https://github.com/rails/rails/security/advisories/GHSA-2gff-2mmg-m73p)): when both headers are present and their first untrusted client addresses differ, it raises `ActionDispatch::RemoteIp::IpSpoofAttackError`, and the request gets HTTP 500. Behind a proxy such as Caddy, which sets `X-Forwarded-For` but passes a client-supplied `Forwarded` header through:

- A request from a public address whose `Forwarded` header names any other address, a private one included, fails with HTTP 500 instead of being served.
- A request from a private address with a `Forwarded` header is served with the address that header names, a loopback address that the Rack::Attack safelist trusts included, because Rails compares the headers only when `X-Forwarded-For` carries an untrusted address.

Since #154 the fork sets `Rack::Request.forwarded_priority = [:x_forwarded]` (`config/initializers/forwarded_header.rb`), the advisory's workaround, which makes Rails and Rack ignore `Forwarded`: `remote_ip` resolves as it did on Rails 8.0, a `Forwarded` header gets no HTTP 500, and the Rack::Attack throttles and safelist use the `X-Forwarded-For` address. The ingress must therefore write `X-Forwarded-For`, as Caddy does; behind a proxy that sent only `Forwarded`, every request would get the proxy's address. Removing the client's `Forwarded` header at the ingress as well is optional.

## Before deployment

1. Confirm that the release being replaced is the Rails 8.0.5.2 checkpoint.
2. Take the normal PostgreSQL and Redis backups.
3. Build the image from the merge commit. The Docker build compiles both the Vite and the Sprockets assets.
4. Run the read-only preflight in the new image against the target database:

   ```sh
   EXPECTED_RAILS_VERSION=8.1.4.1 \
   EXPECTED_CONFIG_DEFAULTS=7.0 \
   EXPECTED_SIDEKIQ_VERSION=7.3.10 \
   EXPECTED_AZURE_SERVICE=AzureBlob \
   bundle exec rails runner script/rails_upgrade/preflight.rb
   ```

   On Rails 8.1 it also checks the tagging, Devise and OmniAuth gem versions, that `to_time` keeps the winter and summer offsets of a daylight-saving timezone, and that Active Job uses the Sidekiq adapter shipped by Sidekiq.

5. Run the Active Storage write/read/delete smoke against the configured service:

   ```sh
   RAILS_UPGRADE_ALLOW_STORAGE_WRITE=true \
   RAILS_UPGRADE_STORAGE_SERVICE=local \
   bundle exec rails runner script/rails_upgrade/active_storage_smoke.rb
   ```

## Deployment

1. Run `bundle exec rails db:abort_if_pending_migrations` with the new image. No migration should be pending.
2. Replace the web container and check health, password login, login with 2FA, API token access, OmniAuth, email reconfirmation, the dashboard, conversation rendering, labels, attachments, Action Cable on the dashboard and the widget, and Super Admin pages.
3. Replace the Sidekiq container. Check immediate and scheduled jobs, and wait for at least one minute-level cron job to be enqueued and performed.

Rails 8.0.5.2 and 8.1.4.1 processes can overlap during the switch, because the schema and persisted formats do not change.

## Post-deployment checks

- The preflight reports Rails 8.1.4.1 and framework defaults 7.0, and the timezone and Sidekiq adapter checks pass.
- Labels on conversations and contacts keep their stored values and API payloads.
- Report totals and time buckets match the Rails 8.0 release, in UTC and in at least one non-UTC account timezone.
- There is no increase in HTTP 4xx/5xx responses, `IpSpoofAttackError` reports, login failures, decrypt errors, Sidekiq retries, or dead jobs.

## Known deprecations

- Devise 4.9.4 calls the routing `resource` DSL with a positional options hash from `devise_for` and `mount_devise_token_auth_for`. Rails 8.1 accepts it and warns that Rails 8.2 will require keywords. `devise-secure_password` 2.2.1 still keeps Devise below 5, so this has to be solved before Rails 8.2.
- MiniMagick loads Ruby's `benchmark` library, which warns that it leaves the default gems in Ruby 3.5.

## Rollback

Rollback is code-only: redeploy the previous Rails 8.0.5.2 image for both web and Sidekiq. Keep the data written during the rollout, since its formats do not change. Then run the preflight with `EXPECTED_RAILS_VERSION=8.0.5.2`.
