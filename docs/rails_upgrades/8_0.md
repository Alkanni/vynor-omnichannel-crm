# Production migration guide: Rails 8.0.5.2

This checkpoint upgrades the fork from Rails 7.2.3.1 to Rails 8.0.5.2 (#129, ported from chatwoot/chatwoot#15151 for CE). It keeps `config.load_defaults 7.0`, the Sidekiq/Redis setup, and every persisted serializer and encryption setting from the Rails 7.2 release. There is no database schema or data migration.

Rails 8.0 security support ends on **November 7, 2026**. Treat this release as a short checkpoint and continue to Rails 8.1.4.1 (#130).

## Application-level changes

- Enum declarations in `app/models` use the positional `enum :name, { ... }` form, which is the only form Rails 8 accepts. Enum names, integer mappings, scopes, and stored values do not change.
- The mailer route is a named `scope`, because Rails 8 rejects `index` on a singular `resource`. The `app_account` and `app_account_conversation` helpers and the `/app/accounts/:account_id/conversations/:id` path are unchanged.
- `config.active_support.to_time_preserves_timezone = :zone` opts into the Rails 8.1 behavior now, so it does not change again in #130.
- `config.action_dispatch.show_exceptions` in the test environment uses the `:all` symbol instead of the deprecated `true`.
- Groupdate moves to 6.8.0. Older releases patch Active Record calculation internals that Rails 8 removed, and reports can then return zero totals.
- Audited 5.8.0, Hairtrigger 1.3.1, Rails I18n 8.0.2, and Sprockets Rails 3.5.2 are the Rails 8 compatible versions.
- `ActionController::ParameterMissing` messages now read "empty or invalid". The exception class and the parameter name do not change.
- The `require(...).permit(...)` strong-parameter API remains supported. `Rails/StrongParametersExpect` is disabled because migrating to `params.expect` changes how malformed requests are rejected.

## Super Admin

- Administrate moves to 1.0.0 and `administrate-field-active_storage` to 1.0.6.
- Administrate 1.0 ships a prebuilt JavaScript bundle with Turbo Drive and Stimulus. The fork's Super Admin templates still rely on the 0.20 behavior: full page loads, `data-method`/`data-confirm` links through jquery_ujs, `js-table-row` clickable rows, and selectize on `field-unit--*` selects. `app/assets/javascripts/administrate/application.js` therefore overrides the gem bundle with the 0.20 Sprockets pipeline (jQuery, jquery_ujs, selectize, and the components in `administrate/components/`).
- `jquery-rails`, `sassc-rails`, and `selectize-rails` are now direct dependencies. Administrate 1.0 no longer depends on them, and the Super Admin SCSS in `app/assets/stylesheets/administrate/` still needs them.
- `administrate-field-belongs_to_search` does not support Rails 8 and is removed. `BelongsToSearchField` renders only the selected record and searches `/super_admin/accounts.json?search=` and `/super_admin/users.json?search=` as the user types, so the Account User form never embeds the whole accounts or users table.

## Security

- Rails 8.0.5.2 fixes the 18 advisories analysed in #114, plus CVE-2026-66066 (GHSA-xr9x-r78c-5hrm), which still applied to 7.2.3.1. Their `.bundler-audit.yml` entries are removed, together with the stale Rails 7.1 entries, and so is the `safe_constantize` backport from #128.
- The application-level Active Storage guards (direct-upload metadata filter, bare direct-upload route block, proxy range limit) stay in place.
- Rails now requires ruby-vips 2.2.1 or newer and native libvips 8.13 or newer, and raises at boot otherwise. The bundle locks ruby-vips 2.3.0, and the Docker image ships libvips 8.15.3.
- BMP, ICO, and PSD attachments stay uploadable and downloadable, but they no longer get thumbnails, because Rails blocks their libvips loaders.
- Inbound email uses the relay ingress and storage uses the local Disk service, so the Mailgun timestamp and GCS CORS changes in this release do not apply.

## Before deployment

1. Take the normal PostgreSQL and Redis backups.
2. Build the image from the merge commit. The Docker build compiles both the Vite and the Sprockets assets.
3. Run the read-only preflight in the new image against the target database:

   ```sh
   EXPECTED_RAILS_VERSION=8.0.5.2 \
   EXPECTED_CONFIG_DEFAULTS=7.0 \
   EXPECTED_SIDEKIQ_VERSION=7.3.10 \
   EXPECTED_AZURE_SERVICE=AzureBlob \
   bundle exec rails runner script/rails_upgrade/preflight.rb
   ```

4. Run the Active Storage write/read/delete smoke against the configured service:

   ```sh
   RAILS_UPGRADE_ALLOW_STORAGE_WRITE=true \
   RAILS_UPGRADE_STORAGE_SERVICE=local \
   bundle exec rails runner script/rails_upgrade/active_storage_smoke.rb
   ```

## Deployment

1. Run `bundle exec rails db:abort_if_pending_migrations` with the new image.
2. Replace the web container and check health, agent login with 2FA, API token access, the dashboard, conversation rendering, attachments, Action Cable on the dashboard and the widget, Super Admin pages, and the Account User remote search.
3. Replace the Sidekiq container. Check immediate and scheduled jobs, and wait for at least one minute-level cron job to be enqueued and performed.

Rails 7.2.3.1 and 8.0.5.2 processes can overlap during the switch, because the schema and persisted formats do not change.

## Post-deployment checks

- The preflight reports Rails 8.0.5.2 and framework defaults 7.0.
- Report totals and time buckets match the Rails 7.2 release, in UTC and in at least one non-UTC account timezone.
- Super Admin pages load their JavaScript and CSS, delete actions still ask for confirmation, and the Account User selects return only matching records.
- There is no increase in HTTP 5xx responses, login failures, decrypt errors, Sidekiq retries, or dead jobs.

## Rollback

Rollback is code-only: redeploy the previous Rails 7.2.3.1 image for both web and Sidekiq. Keep the data written during the rollout, since its formats do not change. Rolling back reopens the advisories that this release fixes, and on 7.2.3.1 only GHSA-8474 is covered by the #128 backport.
