## Reply flow

0. `AiAgentListener#conversation_created`: a new `pending` conversation gets the agent's `welcome_message`, except a conversation a campaign started (`campaign_id` set, #160), which opens with the campaign message. A one-off WhatsApp campaign puts its template in the contact's conversation as an outgoing message (`additional_attributes.campaign_id`), so `ConversationSession#history` shows it as an `assistant` turn when the contact replies.
1. `AiAgentListener#message_created`: for an incoming message in an inbox connected to an agent, while `ConversationSession#ai_active?`, queue `ReplyJob` after `message_await` seconds; otherwise send the pending message.
2. `ReplyJob#perform`: only the job for the newest incoming message answers (bursts get one reply). If the session reached `message_limit`, hand off (`:message_limit`).
3. `ReplyGenerator#perform`: a strict agent first runs the scope check (see below), which may answer the turn itself. Otherwise instructions = behavior + Business Scope Policy (strict agents) + local time (+ the booking calendar of an agent with bookings, #177) + `<knowledge>` + action instructions + reply check rules (strict agents); history from `ConversationSession#history` (`history_limit`, images per `read_file_limit`). One LLM call with a forced function call (`ReplyTool`), because some gateways drop `response_format`. A strict agent's reply then goes through the reply check (see below) before it is returned.
4. `ReplyJob#deliver`: send bubbles (unless silent handoff), apply labels/sheet row/booking/handoff, write an `AiAgent::ReplyTrace`, then queue `WatchJob` with that trace (not after a scope reply), which adds the Watcher's tokens to it. Any error hands off (`:error`) and writes an `error` trace. Generating and delivering run inside a request log run when it is on (see Request log).

## Conversation control (#204)

A `pending` conversation belongs to the inbox's AI agent (`ConversationSession#ai_active?`), so taking a conversation over and handing it back are status changes through the existing `toggle_status` endpoint, with no new route or policy (any user who can open the conversation).
- **Hand back = `pending`:** `Conversation#hand_pending_conversation_to_ai_agent` (`before_save`, updates only) sets `ai_assignee` to `inbox.ai_agent` and clears the human `assignee` whenever an existing conversation in an inbox with an AI agent moves to `pending`, whatever the path: Mark as pending, the header control, bulk actions, automation `change_status`, or a contact writing into a resolved conversation (`Message#reopen_resolved_conversation`). Creating a conversation is unchanged (`set_active_bot_conversation` keeps an explicit assignee). Inboxes without an AI agent, including agent bot inboxes, are unaffected.
- **Take over = `open`:** `toggle_status` `open` already clears `ai_assignee` and self-assigns a user with the agent role (`handle_human_open`); a public human reply does the same through `Message#mark_pending_conversation_as_open_for_human_response`.
- **Message Limit:** while the conversation is `pending`, `ConversationSession#reply_count` counts only AI replies created after `conversations.status_changed_at` (and after the last resolve), so a conversation handed back after the limit gets a fresh limit instead of an immediate `message_limit` handoff. Outside `pending` (the mode where the AI keeps answering after a handoff) it still counts the whole session.
- **Payload:** `meta.ai_agent` = `ConversationSession.event_data(conversation)` = `{ id, name, active }` (`active` = `ai_active?`), or `null` when the inbox has no AI agent, in `api/v1/conversations/partials/_conversation.json.jbuilder` and `Conversations::EventDataPresenter#push_meta` (so ActionCable events and `webhook_data` carry it too). `ai_active?` runs no query for `pending` or non-`open` conversations; only `open` conversations of an agent that keeps answering after a handoff look up the last handoff. `inbox.ai_agent` is read when the payload is built, so in specs an inbox object created before its `AiAgentInbox` caches `nil`: reload the conversation after linking an agent (a real request or job loads it afresh).
- **UI:** `components-next/Conversation/AiAgentAction.vue` in `MoreActions.vue`, left of `ResolveAction`: "AI active" (teal, menu "Take over from AI" → `open`) or "AI off" (menu "Hand over to <agent>" → `pending`), shown only for `open`/`pending` conversations with `meta.ai_agent`. `ConversationCard.vue` shows a teal "AI" badge when `meta.ai_agent.active`. Strings in `i18n/locale/en/conversation.json` (`CONVERSATION.AI_AGENT_ACTION`) and `chatlist.json` (`CHAT_LIST.AI_AGENT_BADGE*`). The AI waits for the next customer message after a hand back; it does not reply at once.

## Business Scope Policy

Per-agent columns, edited in the Business Scope panel of the General tab (#95): `scope_mode` (`off`, the default, or `strict`), `business_description`, `allowed_topics`, `disallowed_topics`. Strict requires the first two; text fields are at most 3,000 characters and blank means nil. `off` adds nothing to the prompt, even when the text fields are filled. For `strict`, `ReplyGenerator#scope_policy` puts `SCOPE_INSTRUCTIONS` (rules in code, shared by replies and the playground) and a `<business_scope>` block right after the behavior. This is a prompt rule, so it asks for compliance and does not guarantee it; the Scope Compliance eval measures it.

Strict also requires `off_topic_message` and `clarification_message` (at most 1,000 characters each), the texts of the scope check below, and `knowledge_gap_message` (same limit), the text of the reply check; all three count as policy columns. Migrations `AddScopeGuardToAiAgents` and `AddReplyValidationToAiAgents` gave strict agents that existed before them an Indonesian default.

Web search (#109): `web_search_enabled` (default false) is valid only with `scope_mode` strict (422 otherwise; the UI turns it off when Strict is turned off), and `web_search_domains` (optional, at most 1,000 characters, host names such as `kompas.com` separated by commas, spaces, or line breaks, `AiAgent#web_search_domain_list`; for Exa's `includeDomains` in EXA-04) is shown under the toggle. Both count as policy columns. `AiAgent#web_search?` is the toggle while `AI_AGENT_EXA_API_KEY` is set, so a blank key turns web search off for every agent, including its scope check rules.

`scope_policy_version` starts at 0 and goes up by one on each update that changes a policy column. A copy keeps the version of its original. The API returns it but does not accept it, and each reply trace stores the version in force, which tells replies before and after a change apart. The policy text itself has no history.

## Scope check (`AiAgents::ScopeGuard`, #96)

- Runs at the start of `ReplyGenerator#perform` for strict agents only, so replies and the playground take the same path; an `off` agent makes no extra call. It is its own model call with the agent's model, temperature 0, and a forced function call whose only field is `decision`, one of `DECISIONS`: `SUSPICIOUS`, `HANDOFF_REQUEST`, `AMBIGUOUS`, `IN_SCOPE`, `GREETING`, `OUT_OF_SCOPE` (the instructions ask for the first that applies, in that order).
- Its prompt is `INSTRUCTIONS` plus the `<business_scope>` block (`AiAgent#business_scope`, shared with the reply prompt), with no behavior, knowledge, or actions. The user message is JSON: `latest_turn` (the customer messages after the last message from the agent's side) and `earlier_messages` (at most `CONTEXT_MESSAGES`, 6, before it, marked customer or agent), so the conversation is data inside string values.
- `OUT_OF_SCOPE` and `SUSPICIOUS` are answered with `off_topic_message`, `AMBIGUOUS` with `clarification_message` (`REPLY_ATTRIBUTES`), as one bubble through `ConversationSession#reply!`, so it counts toward the message limit. Such a scope reply skips the knowledge search, the reply model, and the Watcher, and never hands off. The other decisions go on to the reply model, where the transfer conditions stay the only handoff trigger, and the reply prompt keeps the scope rules, which also cover the off-topic part of a mixed message.
- A latest turn with images (attachments within `read_file_limit`) skips the check, because it cannot see them. A value outside `DECISIONS` or a text answer raises `AiAgents::LlmError`, so `ReplyJob` hands off with `error` and the playground returns 422.
- Web search (#109, EXA-03 of `docs/ai-agent-web-search-decisions.md`): for an agent with `web_search?`, the prompt gets `WEB_INSTRUCTIONS` between `INSTRUCTIONS` and the policy block (two rules that come before the decisions: web search does not widen the allowed topics, so a disallowed topic stays `OUT_OF_SCOPE`, and asking for the contact or personal data of a person or of any other business or service is `OUT_OF_SCOPE`; then a `web_query` for the general part of an `IN_SCOPE` turn, also a mixed one, without names, phone numbers, addresses, e-mail addresses, identity, registration, or serial numbers, or the business's name (an item is only its brand and model), with the business's country for news, safety warnings, and regulations; `""` otherwise). Since #120 the wording names no kind of business, because it reaches every agent with web search. Both rules came from eval runs where a used-car question and a towing number lookup got a web query; without web search the same check also lets those through about 1 in 6 times, and the function schema (`WEB_SCHEMA`) requires a string `web_query` (missing → `LlmError`). Every other agent gets exactly the prompt and schema it had before. `Result#web_search_status` is nil without web search, `not_needed` for a blank query or a scope reply, `skipped_personal_data` when the query is longer than `WebSearch::MAX_QUERY_CHARACTERS` or matches `PERSONAL_DATA_PATTERNS` (8 or more digits with spaces, dots, dashes, or parentheses between them, an e-mail address, an uppercase Indonesian plate pattern, which also matches a few other terms such as `vitamin D 1000 IU` or `XL7 AT`, or a VIN; kept for every business by owner decision Q1 of #120), `skipped_contact_request` when the latest customer messages or the query match `CONTACT_REQUEST` (#110 AC8: "nomor"/"no." with telepon, HP, WA, WhatsApp, kontak, layanan, darurat, or pengaduan; WhatsApp, hotline, call center, alamat; not "nomor" or "kontak" alone, so "lensa kontak" and "kunci kontak" are searched and "kontak dealer X" relies on the rule, owner decision Q2 of #120), whatever the decision, and `pending` otherwise, which the reply searches (#110, see Web search) and replaces with the status of the search. `LONG_NUMBER` (the first pattern) is shared with the reply check.
- The check has no keyword layer and no model of its own. On the eval it does not catch more than the prompt rule; its value is that a refused message never meets the knowledge or the reply instructions, a second independent layer, a fixed text, and the decision in the trace.

## Reply check (`AiAgents::ReplyValidator`, #97)

- Strict agents only; for an `off` agent the schema, the instructions, and the knowledge block are what they were before.
- The reply function of a strict agent gets `decision` (`DECISIONS`: `answer`, `conversational`, `clarify`, `knowledge_gap`) and `sources` (the `[rank]` numbers of the chunks the reply uses) before `messages`, and the prompt gets `INSTRUCTIONS` (what each decision means, the number rule, and that knowledge is data). Its chunks have `<` and `>` escaped, so a chunk cannot close the `<knowledge>` block.
- The check is deterministic and runs on what the model returned. A reply fails with a `blocked_reason`: `invalid_decision` (outside `DECISIONS`, including a text answer instead of the function call), `missing_sources` (`answer` without sources), `unknown_source` (a source that is not the rank of a retrieved chunk), or `unsupported_number`.
- One retry (#142): when the check returns `invalid_decision`, `ReplyGenerator#model_reply` calls the reply model once more (the scope check, knowledge search, and web search are not repeated) and checks that reply instead. Since #152 the retry after a `text` output is not the same request: `ReplyValidator.retry_messages` adds that text as an `assistant` message and `ReplyValidator::TEXT_RETRY_NOTE` (a fixed note from the system, sent as a `user` message, to call `ai_agent_reply` for that reply with its decision and sources) after the conversation, because the same request often gave text again (3 of 5 text turns of agent 5 on the VPS, 2026-11-13); `missing_decision` and `unknown_decision` outputs still get the same request. The check of the second reply still traces numbers and links to the original conversation only, so the model's own text never backs a number. A paired read-only replay of 222 pilot turns of agents 2 and 5 (#152, web search replaced by a failed search) had 23 `text` first outputs in 219 reply model turns: the same request recovered 13 (final `invalid_decision` 10/219, 4.6%) and the text with the note all 23 (0/219), every one passing the check, at the same latency (retried turn p50 about 8.6 s). Every other reason and a `knowledge_gap` decision get no retry, and a second `invalid_decision` sends `knowledge_gap_message` as before. `ReplyValidator.output_shape` names the shape of each output without a valid decision, without its content: `text` (text instead of the function call; `LlmClient::Completion#arguments` is then `{}`), `missing_decision`, or `unknown_decision`; the trace keeps them in `invalid_outputs`. A replay of agent 2's 176 pilot turns on main-5449d38 (#142, read-only) blocked 28 of 173 reply model calls (16.2%) with `invalid_decision`, all `text`, and the failures were mostly not the same turns as in the original traces, so the retry targets model or gateway variance. An `LlmError` on the second call ends the reply like any other model error (error trace and handoff, a playground error). The playground retries inside its request, where `Rack::Timeout` ends it after 15 s, so since #145 it passes `deadline_ms: PLAYGROUND_REPLY_DEADLINE_MS` (14,000) and the reply model is asked again only when the time spent so far plus the first call's `LlmClient::Completion#latency_ms` stays under it; otherwise the playground answers with `knowledge_gap_message` and `validation.retry_skipped: true` (`Trace#retry_skipped?`: an `invalid_decision` with a single invalid output). In the #142 replay, 15 of 31 retried turns ran past 15 s. Live replies have no deadline.
- The number rule: every number in the reply must appear in a cited chunk, in a message of the conversation (customer or agent), or in the current time line of the prompt, or be one of those numbers times a number the customer wrote (A3-01: 4 × Rp25.000). `NUMBER` reads thousands groups, decimals, times, and scale words, so `Price: 25000.00`, `Rp25.000`, `25 ribu`, `25rb`, and `25k` are the same number; list item numbers at the start of a line are skipped. Sums, differences, discounts, numbers written as words, and every non-number claim are not checked.
- Rank markers (#156): models sometimes cite an entry in the reply text although `INSTRUCTIONS` says not to (`[1,2,5]`, `([Sumber](9))` on VPS request logs #196 and #205, whose facts their sources had), and the number rule read those ranks as numbers (`unsupported_number`; `1,2` is the decimal 1.2). `ReplyGenerator#reply_messages`, which gives both the check and the sent bubbles their text, now passes the bubbles through `ReplyValidator.without_rank_markers` for every agent (owner Q1: also `off` agents, whose knowledge entries are numbered too): `RANK_MARKER` (ranks in brackets, or a Markdown link to a rank, with the parentheses around it and the spaces before it) is removed only when all its ranks are entries of the prompt (1 to the knowledge hits plus the web results); a bracket with any other number (`[15]` with 11 entries, `[2026]`) stays and is checked as a number, and a bubble left empty is dropped. The `reply` step of the request log still holds the model output with the marker. A read-only replay of the reply check on the stored outputs of 216 VPS request logs (204 reply, 12 playground, ids 1–246) matched every stored result on main-da530a1 and changed only #196 and #205 (now passing), with no other text change. Other marker shapes (`(Sumber: 9)`, `[Sumber 9]`) are not handled.
- Web results (#110): for an agent with web search, `ReplyGenerator` passes `web_results` (the `WebSearch` items of the prompt, ranked after the knowledge; `[]` for a turn without results), and nil for every other agent, whose check is what it was. A cited rank may then be a web result, and numbers may come from the `text` of cited web results, except runs of 8 or more digits (`ScopeGuard::LONG_NUMBER`: phone, account, identity numbers), which a page never backs; when a reply cites a web result, each such run in the reply also needs the same digits in a cited chunk or the conversation, because a page could hold its parts apart. One more reason: `unknown_url` (a link the model wrote, with its scheme or a bare host with a letter TLD, which chat apps make clickable, also an e-mail domain, that is not a web result URL, a link in the prompt's chunks or the conversation, or the site of a web result such as `kompas.com` for a page on `otomotif.kompas.com`). The model writes no links: after the check, `ReplyGenerator#sent_messages` adds the URL of each cited web result under the last bubble unless the reply already has it, so every cited web result has its link (owner decision on #110, which replaced a planned `missing_citation` reason after models copied long URLs wrongly). Year ranges ("2017 - 2019") are no long number, and the published date of a cited web result backs its numbers. Links compare without scheme, `www.`, trailing slash, trailing punctuation, or case; their digits are left out of the number rule. Residual risks: digits spelled out or split by other separators, and a web number presented as the business's own; the prompt rule covers them.
- `knowledge_gap` and a failed check both send `knowledge_gap_message` as the only bubble; handoff, labels, and the sheet row still apply, because they state nothing to the customer. A reply that is still empty without a handoff raises the empty reply error as before.
- Measured offline on 2,028 stored eval replies before it was enforced (all fixture chunks counted as cited): 2 of 1,664 passing replies would have been blocked (both wrote `Rp0` for free delivery), and 36 failing replies, all off-topic leaks of the `main` variant, would have been.

## Retrieval (`AiAgents::KnowledgeRetriever`)

- Queries (#83): the latest customer turn, plus, when earlier customer turns exist, that turn joined to up to `CONTEXT_TURNS` (2) earlier ones (context at most `MAX_CONTEXT_CHARACTERS`, 1,000; each query at most `MAX_QUERY_CHARACTERS`, 4,000). Messages between two replies are one turn. Agent replies are left out. Each query runs its own lists, and the query with earlier turns counts `QUERY_WEIGHTS` 4 against 1, so a follow-up finds its subject. When the vector and keyword lists of the latest turn have the same top chunk, that turn names its own subject and the weights are `NEW_TOPIC_QUERY_WEIGHTS` 1 and 1 instead (#141): at 4 the chunks of the earlier topic outranked the new question's, most of all on large Q&A knowledge that asks the same questions about many services (VPS agent 2, 1,575 Q&A: in a replay of its captured lists, new-topic turns with their Q&A at rank 1 went from 22 to 39 of 68). A follow-up that leaves out its subject rarely gets the same top chunk from both lists, and no multi-turn or topic change case of the retrieval eval that existed before #141 changed rank. Keyword mode has no vector list, so it always uses `QUERY_WEIGHTS`. Both queries are embedded in one request. There is no LLM query rewriting.
- Hybrid mode when `AI_AGENT_EMBEDDING_MODEL` is set (#82): two lists, each the top `CANDIDATES` (40) chunks with the current `embedding_model` (`KnowledgeChunk.searchable`), or the top `context_limit` when it is higher, are fused with weighted Reciprocal Rank Fusion. The vector list is pgvector cosine `nearest_neighbors`, weight 1; the keyword list is `KnowledgeChunk.keyword_ranked`, weight `KEYWORD_WEIGHT` (0.5). A chunk scores `weight / (RRF_K + rank)` per list (`RRF_K` 20), and only the top `context_limit` chunks (default 8) reach the model, the Retrieval Test, the playground, and the trace (#103). The fusion settings were chosen on lists of 40, and lists of 10 or 20 ranked some answers lower, so the candidates stay 40 whatever the limit. In the #103 sweep 5 and 8 chunks answered as well as 40 (3 lost facts on questions about three or four products) with about half the input tokens; migration `ChangeAiAgentsContextLimitDefault` moved agents still at 40 to 8. Score = RRF score in both modes (higher is closer, a rank measure rather than a relevance measure).
- Keyword mode otherwise: `KnowledgeChunk.keyword_ranked` lists alone, through the same fusion.
- Context expansion (`AiAgents::ContextExpansion`, #134): with `context_expansion_radius` (per agent, 0–3, default 0) above 0, the chunks up to that distance before and after each match (anchor) of the top `context_limit` are added, only from the same `section` of the same source and from `searchable(embedding_model)`; Q&A, products, and chunks with a nil `section` get none. `context_limit` stays the total sent (owner decision 1a), so a neighbor at distance d of the match ranked r competes as rank `r + d * NEIGHBOR_STEP` (1), behind the match of that rank; a neighbor that is also a match counts once, as a match. The thresholds apply to the matches only (2a). The hits are then ordered as runs of consecutive chunks of one section in document order, runs by their best match, and `Hit#rank` is the place in the prompt (1..n, so web ranks still start after `hits.size`); a neighbor has no `score` and `neighbor_of` = the prompt rank of its match. Radius 0 skips all of it, so hits, ranks, scores, and prompt are exactly those of the search. In evals/ai-agent (#134) radius 1 sent every fact that Context Limits 3 (hybrid) and 5 (keyword) missed, and kept the match ranking (hit@k/MRR) unchanged, but at the default limit 8 it sent one more control case a paragraph that does not answer it and one reply followed a neighboring paragraph about another channel (C-RT03), so the default stayed 0 (owner gate); an admin turns it on per agent (General → Additional Settings) when the Retrieval Test shows an answer continuing in the next chunk.
- `keyword_ranked` is `ts_rank` with `TEXT_SEARCH_CONFIG` (`indonesian`, which stems word forms and has no stop words) and OR-joined terms, not BM25. It computes `to_tsvector` per chunk of the agent at query time, about 50 ms per 1,000 chunks; there is no text search index, because a GIN index would need an `@@` filter and `ts_rank` would still recompute the vector.
- Only relevant chunks enter a list (#81): the keyword list drops chunks with `keyword_rank` 0, the vector list drops chunks farther than `AI_AGENT_EMBEDDING_MAX_DISTANCE` (blank keeps all). A chunk past the distance limit still comes back through the keyword list when it shares a word with the query. With no chunk left the prompt has no `<knowledge>` block; an agent that has knowledge still gets `NO_RELEVANT_KNOWLEDGE_INSTRUCTIONS` (state facts only from the conversation, otherwise say it does not know).
- Chunking (`TextChunker`, #84): at most 1,500 characters plus the source title prefix. A Markdown heading starts a chunk and every chunk opens with its heading path (`Panduan > Cabang Dago > Kontak`). Heading text is never lost (#92): a heading with nothing under it becomes its own chunk unless the deeper heading after it carries it in its path, and a path over `MAX_HEADING_PATH` is shortened on its chunks and kept in full once. A table longer than a chunk is split between rows with its header repeated. Paragraphs of a section are packed, and anything longer is cut at whitespace. Q&A and products are one chunk each. `TextChunker.split` returns `Chunk(section, text)`: `section` numbers the stretches between headings from 0 (text without headings, such as a PDF, is one section), and `KnowledgeIndexer` stores it on `ai_agent_knowledge_chunks.section` (nil for Q&A and products) (#134). Website content is Markdown from `WebsiteContentExtractor`; DOCX becomes Markdown in `DocxMarkdown`, which finds headings by style name because style ids are localized (`Judul1`). PDF has no structure to use.
- Products (#121): price, weight (grams), and stock are nullable without a default. `KnowledgeIndexer.product_text` writes `Product:`, then `Price: <currency> <2 decimals>`, `Weight: <n> grams`, and `Stock: <n>` only for recorded values (0 included), then the description. Migration `20261118000000` set weight 0 to NULL and left price and stock 0 alone (owner decision Q1); `Migration::ReindexAiAgentProductsJob` marks product chunks as outdated so they are rewritten without a search gap.
- A change to chunking does not reach existing chunks by itself, because `KnowledgeIndexer` skips records whose version matches. `Migration::RechunkAiAgentsJob` shows the pattern: it marks chunks as made from an older version, so they are replaced source by source and stay searchable until then (Knowledge Health shows them as `outdated`). Such a job must not use `resync!`: `KnowledgeIndexer` removes the chunks of a source that is not `ready`, so it re-extracts DOCX in place and a file that cannot be read keeps its text and chunks (#92). `Migration::BackfillAiAgentChunkSectionsJob` (#134, enqueued by a migration) is the pattern without re-embedding: it chunks each text, website, and file source again and writes the sections only when the new chunks equal the stored ones of the current version; other chunks keep a nil `section` (no neighbors) until their next indexing.

## Reply traces (`ai_agent_reply_traces`)

One row per answered customer message: `status` (`replied`, `handoff`, `message_limit`, `error`), `model`, `scope_policy_version`, `scope_decision` and `scope_latency_ms` (nil when the check did not run), `web_search_status` (the search's status for a searched turn: `searched`, `cached`, `skipped_budget`, `failed_*`; else the scope check's: `not_needed`, `skipped_personal_data`, `skipped_contact_request`, or `shadow` on rows from #109; nil for an agent without web search or when the check did not run, and the query itself is never stored), `web_results` (jsonb list of `rank`, `url` of the web results in the prompt; empty otherwise), `web_latency_ms` (the Exa request; nil when none was made) and `web_cost_usd` (decimal, what Exa charged; 0 for a cached, skipped, or failed search) since #110, `reply_decision`, `cited_ranks` (jsonb list of ranks), and `blocked_reason` (nil and empty unless the reply check ran; `reply_decision` is nil for a decision outside the list; with a retry they describe the second reply), `invalid_outputs` (#142: jsonb list of the shapes `text`, `missing_decision`, `unknown_decision` of each reply model output without a valid decision, in order; one entry when the model was asked again, two when the second output had none either, empty otherwise and on older rows), `retrieval_mode`, `embedding_model`, `retrieved` (jsonb list of `chunk_id`, `chunkable_type`, `chunkable_id`, `rank`, `score`, and since #134 `neighbor_of` (the rank of the match a neighbor was sent for, nil for a match, whose `score` a neighbor lacks); empty and nil mode for a scope reply), `labels`, `input_tokens`/`output_tokens` (scope check + reply model, both calls when it was asked again; nil when the gateway sends no `usage`), `scope_input_tokens`/`scope_output_tokens` (the scope check's share), `cached_input_tokens` (scope check + reply model input read from the provider's prompt cache; nil when the gateway does not report it), `watcher_input_tokens`/`watcher_output_tokens`/`watcher_cached_input_tokens` (the Watcher call after the reply; nil when it did not run or failed), `latency_ms` (scope check + retrieval + web search + model calls), `error_class`. RubyLLM reports `input_tokens` without the cached part (`prompt_tokens` less `cached_tokens`), so the whole prompt is `input_tokens + cached_input_tokens`. The `scope_*`, `cached_*` and `watcher_*` columns exist since #102 and are nil on older rows. No message or chunk content is stored, so the search queries are not stored either; they follow from the conversation. Rows are deleted with their agent or conversation (`dependent: :delete_all`); no time-based retention. Not written for the playground, or when a reply is dropped because the customer wrote again.

`bundle exec rails ai_agents:usage_report` (#102) prints `AiAgents::UsageReport` as Markdown for a period (`FROM`/`TO`, ISO 8601, UTC unless an offset is given, default the last 7 days, `TO` excluded) and optionally one agent (`AGENT_ID`). Per agent: traces by status, models, model calls and their input/output tokens (total, p50, p90) for the scope check, the reply model (trace total less the scope share; old strict rows without the scope share are left out) and the Watcher (counted by its tokens), cached input share, reply and scope latency (p50/p95), knowledge chunks sent per reply model call and how many of them were neighbors of a match (#134), scope and reply decision counts, for an agent with web search (#110) the share of its web search turns that had a query, the statuses, and the Exa requests with spend and latency (p50/p95), and tokens and model calls per conversation and per conversation without a handoff: one with a `replied` trace in the period and no `handoff`, `message_limit` or `error` trace in it. A failed model call ends in an `error` trace and is not counted as a call. The second reply model call of a turn that was asked again (#142) is not counted apart either; its tokens are in the trace's, and `invalid_outputs` tells those turns. No message or knowledge content is printed.

## Request log (`ai_agent_request_logs`, #147)

A Logfire-like record of what went into and came out of each step, kept in the same Postgres, only while `AI_AGENT_REQUEST_LOG_ENABLED` is on (default off). Unlike reply traces it stores content: customer messages, prompts, model outputs, chunk texts, web queries and results. Only Super Admins may read it, in the read-only viewer of #148 (see Viewer below); there is no API or serializer for it.
- **Runs:** `AiAgents::RequestRecorder.record(ai_agent:, source:, input:, **links) { |log| ... }` opens one run per entry point and writes one row when it ends, also when it raised (`status: error`, `error_class`, the steps so far, empty `output`), then re-raises. `source`: `reply` (`ReplyJob#reply`, after the message limit check; `input` = history, `output` = bubbles sent, handoff, labels, sheet row; links `conversation_id`, `message_id`, and `reply_trace_id` of the trace written in `deliver`; a reply that raised has no trace link), `watcher` (`WatchJob`, linked to the reply's trace; `output` = actions), `playground` and `retrieval_test` (controller, no conversation; the Retrieval Test's `output` is the hit count and web search status), `indexing` (`KnowledgeIndexer#perform`, `input` = embedding model).
- **Steps:** `RequestRecorder.step(name, input, model:) { |step| step.output = ...; step.tokens = ... }` appends `{step, started_ms, latency_ms, input, output, model, tokens, error_class}` in the order steps end; outside a run it only yields. Recorded by `LlmClient#chat` (`step:` keyword: `scope_check`, `reply` (one per call, so a retry is two; since #152 the input of a retry after text ends with the retry messages), `watcher`; input temperature, instructions, messages, schema name exactly as sent; output the completion content; tokens input/output/cached_input), `LlmClient#embed` (`embedding`: input type and prefixed texts; output vector count and dimensions, never the vectors), `KnowledgeRetriever#hits` (`retrieval` after its embedding step: mode, queries; hits with rank, chunk/chunkable ids, score, distance, neighbor_of, content; no step when there is nothing to search), `WebSearch#perform` (`web_search`: provider, query, domains; status, results with provider rank and prompt text, latency, cost), `ReplyValidator#perform` (`reply_check`: sources; decision, blocked reason). A step inside another step is not recorded on its own: `KnowledgeIndexer#embed` records one `embedding` step per batch (chunkable, chunk count, dimensions) that hides the client's step, so chunk texts stay out.
- **Serialization at write time:** images (`RubyLLM::Content` attachments, history blobs) become `{blob_id, filename, content_type, byte_size}`. With `AI_AGENT_REQUEST_LOG_MASK_PII` on, Indonesian mobile numbers, `+`-prefixed numbers, and e-mail addresses in every string are replaced by `[phone]`/`[email]`; the model payload is unchanged. No API key or header is recorded, and errors keep only their class.
- **Isolation:** a failed write is reported to `ChatwootExceptionTracker` and swallowed, so it never reaches `ReplyJob`'s rescue (which would hand off). The run only adds one insert at its end.
- **Retention:** `AiAgent::RequestLog::RETENTION` = 30 days; `AiAgents::RemoveOldRequestLogsJob` (`config/schedule.yml`, daily 20:00 UTC, queue `purgable`) deletes older rows in batches of 1,000. Rows also go with their agent or conversation (`dependent: :delete_all`). Indexes: `created_at`, `(ai_agent_id, created_at)`, `conversation_id`.
- **Viewer (#148):** `SuperAdmin::AiRequestLogsController` (`/super_admin/ai_request_logs`, `index`/`show` only, sidebar item "AI Request Logs" next to Push Diagnostics; auth is the Super Admin devise session of `SuperAdmin::ApplicationController`). The list filters by `account_id`, `ai_agent_id`, `source`, `status`, `conversation` (the dashboard number, `display_id`), and `from`/`to` (ISO dates, UTC; another format gives 422), newest first, 25 per page (Kaminari). It reads `AiAgent::RequestLog.summaries`, which leaves out `steps` and sums the input and output tokens of the steps in SQL as `total_tokens`; the snippet is `#last_customer_message` from `input`. The detail page (`app/views/super_admin/ai_request_logs/`) shows the run's meta (conversation link `/app/accounts/:account_id/conversations/:display_id`, message and reply trace ids), its input and output, and each step in the order of `steps` with an SVG bar for `started_ms`/`latency_ms` within the run, inside a `<details>`: strings such as prompts as text with whitespace kept, everything else as pretty JSON, a hits table for `retrieval` and a results table for `web_search`. All content goes through ERB escaping. The empty state says whether `AI_AGENT_REQUEST_LOG_ENABLED` is on.

## Bookings (#177)

An agent records booking requests when `booking_enabled` is on **and** its account has the `bookings` feature (`AiAgent#booking?`; `config/features.yml`, `feature_flags_ext_1`, off by default, switched in Super Admin or Settings → Features). Turning the feature off stops every agent of the account. Staff see and confirm bookings on the Bookings page and in the conversation panel (#178, see Staff below).

- **Settings** (General tab, panel shown only with the feature): `booking_conditions` (required while on, ≤ 3,000), `booking_label_id` (a label of the account, required while on; a label deleted later is skipped, like `allowed_label_ids`), `booking_fields` (≤ 10 extra field names, trimmed, 1–50 characters on one line, unique case aside, none of the core names `customer_name service date time notes`), and the status messages `booking_confirmed_message` / `booking_cancelled_message` (#185, see Status messages below). No foreign key on the label.
- **Action** (`AiAgents::ActionSchema`): `create_booking` (boolean) + `booking` (object of strings: the core fields and `booking_fields`; with held bookings also `replaces_booking`, a reserved core name) + `cancel_booking` (string, only with held bookings, #195), with `BOOKING_INSTRUCTIONS` (summary first, then a booking only after the customer confirmed it; no phone number asked; times in messages as the customer wrote them; no prices or totals the customer did not ask for; a confirmed change is a new request; tell the customer the staff will confirm; last, ask the customer's name before the summary when the conversation does not give it (#189: written into the first sentence instead, it raised replies blocked for unrequested prices on B-BK-06 from 3/15 to 10/15 against main), the condition, and the conversation's `requested`/`confirmed` bookings (`ConversationSession#bookings`; none in the playground) listed as `#<id> service, local time, status`; with held bookings `HELD_BOOKING_INSTRUCTIONS` follows (#195: the numbers are for `replaces_booking`/`cancel_booking` and never for the customer). Without held bookings the prompt and schema are exactly those before #195: an always-on version cost booking eval positives 67/80 vs 73/80 on main. `#parse` (`#booking_request`) returns `booking` = the attributes of a `Booking` (`service`, `customer_name` (may be blank, see Recording), `scheduled_at` from `date` `YYYY-MM-DD` + `time` `H:MM`/`HH:MM` 24-hour in the agent's time zone, `notes`, `details` = the extra fields), or, when `create_booking` is true but it cannot be one, `booking_rejection` = `invalid_schedule` (date or time missing or not parsing, also a `booking` that is not an object), `past_schedule` (`scheduled_at` not after `Time.current`, #190; only the AI path, `Booking` itself accepts any time), or `missing_service`; both nil when `create_booking` is not true (#189 replaced #177 AC7's silent drop). The booking carries `rescheduled_from_id` and `#parse` returns `booking_cancellation`, each only when the number names a booking the conversation still holds (`#held_booking_id`, `12` or `#12`), else nil (#195). `ReplyGenerator::Reply#actions` is the hash `apply!` takes (also the request log output).
- **Calendar** (`ActionSchema#calendar`): today and the next 14 days as `Weekday YYYY-MM-DD`, the first three named today / tomorrow / the day after tomorrow. `ReplyGenerator` puts it after the time line and passes it to the reply check with the current time, so a summary that turns "besok" into its date is not `unsupported_number`; the Watcher gets it in its instructions. With it, `ActionSchema#known_text` gives the check the booking condition and the held booking lines exactly as the prompt lists them (#201), so a reply may state the arrival hours of the condition, or restate a held booking whose messages have left the context window. Before #201, VPS request log #381 sent the knowledge gap message for "jam kedatangan antara 07.30–18.00", which came from the condition. A replay of the 363 stored VPS runs changed only that run, and none became blocked. Trade-off: for booking agents the day numbers of those 15 days, the month, the year, and every number of the condition and the held booking lines count as known numbers. Every other agent gets the prompt, schema, and check it had before.
- **Recording** (`ConversationSession#apply!(booking:)` from `ReplyJob` and `WatchJob`): inside a transaction holding the conversation's row lock (`Conversation.lock.find`, so the record in hand stays as it is), a booking with the same `scheduled_at` and service (case aside) as a `requested`/`confirmed` one of the conversation is skipped; otherwise a `Booking` is created (`requested`, the conversation's contact, the agent, `customer_name` from the model or else the contact's name, stripped; anonymous widget contacts carry a generated Haikunator name), the booking label is added as the agent (`Current.executed_by`), and an activity message `ai_agents.bookings.requested` names the booking id, service, and local time. Like labels, a booking applies even when the reply failed the check; the customer then gets the knowledge gap message. **Reschedule** (#195): inside the same lock, `#reschedule!` marks the held booking named by `rescheduled_from_id` `rescheduled` (no customer message, no staff activity) and the new booking keeps the link; a booking the staff changed meanwhile is not replaced and the new one has no link; the activity becomes `ai_agents.bookings.rescheduled` ("…which replaces booking #N"). **Cancellation requests** (#195, `#request_cancellation!`): the booking stays as it is; booking label + activity `ai_agents.bookings.cancellation_requested` with marker `ai_agent_booking_cancellation`, once per customer message (`#noted_since_customer_wrote?`, shared with rejections); staff cancel it. **Rejections** (#189, `ConversationSession#reject_booking!`): a `booking_rejection`, or a booking whose name stays blank (`missing_customer_name`), adds the booking label and an activity message `ai_agents.bookings.rejected` with the reason (`ai_agents.bookings.rejection_reasons.*`) and marker `ai_agent_booking_rejected`; no booking and no handoff, and the reply is sent unchanged. At most one per customer message: a rejection after the latest incoming message already has one is skipped, so the reply and the Watcher do not both note it.
- **Data**: `bookings` (account, conversation, contact, nullable `ai_agent`, `status` enum `requested confirmed cancelled completed no_show rescheduled` (5, #195), `rescheduled_from_id` (nullable, indexed, migration `20261121000000`), `scheduled_at` UTC, `service`, `customer_name`, `notes`, `details` jsonb). Deleted with the conversation (`dependent: :delete_all`); kept with `ai_agent_id` nulled when the agent is deleted; moved to the base contact by `ContactMergeAction#merge_bookings` (#182). The request log output and the playground response carry `booking` and `booking_rejection`.
- **Staff** (#178, #196): `GET/POST/PATCH /api/v1/accounts/:account_id/bookings` + `GET …/bookings/fields` (`Api::V1::Accounts::BookingsController`). `BookingPolicy` needs the feature (401 without it) and scopes bookings to the conversations a user can open (`Conversations::PermissionFilterService`: administrators all, agents their inboxes; anything else is 404). `index`: filters `status` (one or several), `from`/`to` (ISO 8601 times, `to` excluded; the frontend sends local day starts), `contact_id`; ordered by `scheduled_at`; 25 per page; `meta.count`, `meta.current_page`; 422 for an unknown status or a time that does not parse. `create` (#196) takes `conversation_id` (required, 422 "Missing conversation_id" without it, also for `fields`; the display id, found within the user's conversations, else 404) and the fields, records a **confirmed** booking with the conversation's contact and `ai_agent = conversation.inbox.ai_agent`, writes `bookings.activity.created`, and sends no customer message (201, the booking JSON); `fields` returns that inbox agent's `booking_fields` (none without an agent); field input is validated at the boundary (`#validate_fields`: text only, stripped, blank notes as nil, `scheduled_at` ISO 8601, `details` names with text; 422 otherwise; a past time is accepted). `update` without `status` but with fields edits them (`Booking#edit!`: no status change, no customer message, activity `bookings.activity.edited` with each field before → after, nothing when unchanged; 422 for a booking without next statuses); `update` with `status` changes only the status (422 otherwise), and only the booking's own or one of `Booking::NEXT_STATUSES` (#191: requested → confirmed/cancelled/completed/no_show, confirmed → cancelled/completed/no_show, completed ↔ no_show, cancelled and rescheduled final, nothing back to requested; 422 "A … booking cannot become …" otherwise; every booking JSON carries `next_statuses`), and calls `Booking#change_status!`, which writes an activity message naming the user (`bookings.activity.status_changed`) and sends the status message (see below), and nothing when the status stays. Frontend: route `bookings_index` (`routes/dashboard/bookings/`, administrators and agents), sidebar entry and page check the flag themselves because a community install shows routes whatever their `featureFlag` (`usePolicy#shouldShow`), the page waits for the account's features before its first fetch; conversation sidebar item `bookings` (`components-next/Bookings/ContactBookings.vue`, the contact's bookings, upcoming first); page and panel show "Replaces booking #N" for `rescheduled_from_id`, and the Rescheduled status gets its own tab (#195); `BookingFormDialog.vue` (#196: new or edit, local date/time inputs via `localDateTime`, agent fields, opened from the panel's Add booking button and the Edit buttons of the page and panel for bookings with next statuses); `BookingDetailDialog.vue` (#208: read-only, opened from the View details button of every page row, final bookings too; shows the row as loaded, no request: status, "Replaces booking #N", schedule, service, customer name, contact name and phone, each `details` field, AI agent, created time, notes with line breaks, conversation link; `-` for a blank value); shared `BookingStatusMenu.vue` (offers the status and its `next_statuses` only, no menu once none is left, and an alert `Dialog` before `BOOKING_FINAL_STATUS` cancelled, #191), `constants.js`, `helpers.js`, i18n `en/bookings.json`.
- **Status messages** (#185): `AiAgent::BOOKING_MESSAGES` maps `confirmed` / `cancelled` to the agent's `booking_confirmed_message` / `booking_cancelled_message` (text ≤ 5,000, blank by default = no message; must parse as Liquid, else 422 `ai_agents.bookings.invalid_message`, because `Liquidable` swallows syntax errors and would send the raw text). ## Web search (providers)

`AiAgents::WebSearch` (#108, EXA-02 of `docs/ai-agent-web-search-decisions.md`; providers since #126) searches through the provider named in `AI_AGENT_WEB_SEARCH_PROVIDER` (`PROVIDERS`: `exa` default, `tavily`, `brave`, `perplexity`), each a subclass of `AiAgents::WebSearch::Provider` in `app/services/ai_agents/web_search/` that builds the request (`Provider::Request(verb, url, body)`), sets the auth headers, normalizes a 200 answer to `{title, url, published, snippets}`, and states the cost in USD (Exa `costDollars.total`; Tavily US$0.008, Brave and Perplexity US$0.005 list price per search) and whether an answer means its credits are gone (402 for all; Tavily 432/433; Brave `error.code` `QUOTA_LIMITED`/`USAGE_LIMIT_EXCEEDED`/`CREDIT_EXHAUSTED`). Exa posts `{query, type: lite, numResults: 3, userLocation: ID, contents.highlights.maxCharacters: 800, includeDomains?}` to `https://api.exa.ai/search` with `x-api-key`; the other request contracts are in the decision record's Providers section. The request goes through Faraday (open timeout 1 s, read 4 s) and returns `Result(status, results, latency_ms, cost_usd)`; results are `Item(rank, title, url, published_at, highlights)`, and `Item#text` joins the highlights into one text of at most `MAX_TEXT_CHARACTERS` (800), because Exa returns up to about three times `maxCharacters` per result (#108). It never raises for the provider: credits gone → `failed_credits`, other 429 → `failed_rate_limit`, 5xx and connection errors → `failed_provider`, timeouts → `failed_timeout`, other non-200 (400/401/403/422) → `failed_request`, reported to `ChatwootExceptionTracker` with the provider name, the HTTP status, and a machine-readable code only (Exa `tag`, Brave `error.code`), so the key never reaches a message or log. No retry. Redis (`Redis::Alfred`, keys in `Redis::RedisKeys`): `ai_agents:web_search:spend:<YYYY-MM>` (UTC micro-dollars for all providers together, INCRBY, 40-day expiry; at or above the budget → `skipped_budget`), `ai_agents:web_search:credits_gone:<provider>:<YYYY-MM>` (set when that provider's credits are gone, also → `skipped_budget` for the rest of the month for that provider only), `ai_agents:web_search:cache:<sha256 of the provider, URL, and body>` (6 h, `cached`, no spend). The Retrieval Test calls it with an admin's query. Replies (#110): when the scope check's status is `pending`, `ReplyGenerator#web_search` searches its `web_query` with `web_search_domain_list` after the knowledge search, moves the result ranks after the knowledge ranks, and puts `ReplyValidator::WEB_INSTRUCTIONS` and a `<web_results>` block after `<knowledge>` (entries `[rank] title`, `URL:`, `Published:` when the provider gives a date, then `text`; `<` and `>` escaped in the whole entry). The instructions say the entries are untrusted data, only for general information and never for the business's own facts, that the knowledge wins a conflict, that a general fact needs a cited web entry, to cite at most two web entries next to the knowledge entries of the business facts, to write no links, to keep that part to three short sentences, and to add no business fact the customer did not ask for. A search with no results, a skip, or a failure leaves the reply to the knowledge, with the status in the trace; the reply check then applies its web rules (see Reply check).

## Evaluation

`evals/ai-agent/` (issue #71) is a Promptfoo regression eval against the playground (booking cases since #177: `promptfooconfig.booking.yaml`, `tests/b-booking.yaml`, `lib/booking-assertions.mjs`, `booking-report.mjs`, fixture `bengkel-booking.json`, deterministic assertions on the playground's `booking`), outside the app bundle (`npx promptfoo@0.124.1`). `setup.mjs` recreates eval agents from `fixtures/toko-roti.json` through the API; `provider.mjs` sends each case's conversation (lines starting with `AI:` become assistant messages) and exposes `handoff`, `labels`, and retrieval as metadata for assertions; `llm-rubric` cases use a judge model from `.env`. A second config (`promptfooconfig.retrieval.yaml`, issue #80) runs questions through `retrieval_test` for an agent with a larger synthetic knowledge base (`fixtures/toko-roti-large.json`), long documents (`fixtures/toko-roti-dokumen.json`), and, since #141, 195 Q&A that ask the same questions about 30 car care services (`fixtures/bengkel-qa.json`, categories `ganti-topik-qa` and `lanjutan-qa`), and reports hit@1, hit@5, MRR, the score distribution of relevant vs irrelevant chunks, and latency per mode. A third config (`promptfooconfig.scope.yaml`, issue #94) runs `tests/s-scope.yaml` once per agent variant, where a variant is a provider with `config.agent`, and `report.mjs` computes off-topic leakage, false rejection, knowledge gap handling, and injection success per variant from the `metric` tag of each assertion, plus the scope check's latency (p90) and decision counts, the reply check's decision and `blocked_reason` counts, and the tokens of the scope check and the reply model apart and the cached input share (#102). A fourth config (`promptfooconfig.web.yaml`, issues #106, #109, and #110) runs `tests/w-web.yaml` against a strict car workshop agent with web search (`fixtures/bengkel-mobil.json`) whose allowed topics include general car information: each case has a `route` (`internal`, `web`, `blocked`); the `route` assertion passes when the scope check's decision matches its `scope` label and it wrote a `web_query` exactly for the `web` route, and the `pii` assertion when the query has none of the case's `pii` strings; `links` and `citation` (`lib/web-assertions.mjs`, #110) check the links of the sent reply as the reply check does; `report.mjs` adds route accuracy, web queries of blocked cases, web search status per category, false skips, `web` route cases answered from web results, the link checks, entries and characters per web block, reply model tokens with and without a web block, Exa latency, and the run's Exa spend. Since #111 the `web` route cases also have a `web_claims` `llm-rubric` (defined once on W-WB-01 as a YAML anchor); its assertion `transform` (`lib/web-assertions.mjs:judgeInput`) gives the judge of `promptfooconfig.web.yaml` the reply, the web results it cites, and the knowledge chunks from the provider metadata, and `report.mjs` starts with the EXA-05 gate table (route accuracy, searches of `phone` and other `blocked` cases, personal data sent to Exa, `web_claims` over replies answered from the web, p90 output tokens of those replies). The web search (Exa) is specified in `docs/ai-agent-web-search-decisions.md`, whose runbook section covers activation, kill switches, the usage report, rollback, and the VPS steps (EXA-05, #111). A fifth config (`promptfooconfig.context.yaml`, issue #133) runs `tests/c-context.yaml` against the `konteks` agent (`fixtures/toko-roti-konteks.json`: sections longer than one chunk, text without headings cut mid-sentence, one-chunk controls, and documents on neighboring topics, 69 chunks): each case lists the facts its answer needs with the chunk each sits in (Knowledge Preview position); the `context` assertion passes when all were in chunks sent to the reply model and `noise` (controls) when none of the texts around the answer were, and `context-report.mjs` reads the chunks through the Knowledge Preview API to check the recorded positions and report context recall, full context rate, completeness, noise, knowledge characters, and, for facts not sent, the distance to the nearest sent chunk of the same section with an estimate for ±1/±2/±3 neighbors; it is the baseline for neighbor expansion (#134). The end-to-end, scope, and context configs share the judge in `judge.yaml`. See its README for running and comparing baselines, and for the release gate.

## Configuration

Installation configs (Super Admin): `CAPTAIN_OPEN_AI_API_KEY`, `CAPTAIN_OPEN_AI_ENDPOINT`, `AI_AGENT_MODELS` (gateway model IDs), `AI_AGENT_EMBEDDING_MODEL`, `AI_AGENT_EMBEDDING_MAX_DISTANCE` (cosine distance, validated in `InstallationConfig`), `AI_AGENT_EMBEDDING_ENDPOINT`, `AI_AGENT_EMBEDDING_API_KEY`, `AI_AGENT_WEB_SEARCH_PROVIDER` (select, default `exa`), `AI_AGENT_WEB_SEARCH_API_KEY` (secret, the chosen provider's key, renamed from `AI_AGENT_EXA_API_KEY` by migration `20261106070000` in #126; blank turns web search off), `AI_AGENT_WEB_SEARCH_MONTHLY_BUDGET` (USD, default 8, validated in `InstallationConfig`), `AI_AGENT_REQUEST_LOG_ENABLED` and `AI_AGENT_REQUEST_LOG_MASK_PII` (booleans, default off, saved as text by Super Admin and cast in `RequestRecorder`; #147). `AI_AGENT_PRODUCT_CURRENCY` (#121, ISO 4217 code validated in `InstallationConfig`, blank means `IDR`, `AiAgent::Product.currency`) is the currency of every product price, in the product chunks and the product list. Per-agent settings are the `AiAgentsController::SETTINGS` columns.
