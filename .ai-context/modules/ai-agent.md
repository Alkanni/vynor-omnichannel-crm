## Reply flow

1. `AiAgentListener#message_created`: for an incoming message in an inbox connected to an agent, while `ConversationSession#ai_active?`, queue `ReplyJob` after `message_await` seconds; otherwise send the pending message.
2. `ReplyJob#perform`: only the job for the newest incoming message answers (bursts get one reply). If the session reached `message_limit`, hand off (`:message_limit`).
3. `ReplyGenerator#perform`: a strict agent first runs the scope check (see below), which may answer the turn itself. Otherwise instructions = behavior + Business Scope Policy (strict agents) + local time + `<knowledge>` + action instructions + reply check rules (strict agents); history from `ConversationSession#history` (`history_limit`, images per `read_file_limit`). One LLM call with a forced function call (`ReplyTool`), because some gateways drop `response_format`. A strict agent's reply then goes through the reply check (see below) before it is returned.
4. `ReplyJob#deliver`: send bubbles (unless silent handoff), apply labels/sheet row/handoff, write an `AiAgent::ReplyTrace`, then queue `WatchJob` with that trace (not after a scope reply), which adds the Watcher's tokens to it. Any error hands off (`:error`) and writes an `error` trace.

## Business Scope Policy

Per-agent columns, edited in the Business Scope panel of the General tab (#95): `scope_mode` (`off`, the default, or `strict`), `business_description`, `allowed_topics`, `disallowed_topics`. Strict requires the first two; text fields are at most 3,000 characters and blank means nil. `off` adds nothing to the prompt, even when the text fields are filled. For `strict`, `ReplyGenerator#scope_policy` puts `SCOPE_INSTRUCTIONS` (rules in code, shared by replies and the playground) and a `<business_scope>` block right after the behavior. This is a prompt rule, so it asks for compliance and does not guarantee it; the Scope Compliance eval measures it.

Strict also requires `off_topic_message` and `clarification_message` (at most 1,000 characters each), the texts of the scope check below, and `knowledge_gap_message` (same limit), the text of the reply check; all three count as policy columns. Migrations `AddScopeGuardToAiAgents` and `AddReplyValidationToAiAgents` gave strict agents that existed before them an Indonesian default.

`scope_policy_version` starts at 0 and goes up by one on each update that changes a policy column. A copy keeps the version of its original. The API returns it but does not accept it, and each reply trace stores the version in force, which tells replies before and after a change apart. The policy text itself has no history.

## Scope check (`AiAgents::ScopeGuard`, #96)

- Runs at the start of `ReplyGenerator#perform` for strict agents only, so replies and the playground take the same path; an `off` agent makes no extra call. It is its own model call with the agent's model, temperature 0, and a forced function call whose only field is `decision`, one of `DECISIONS`: `SUSPICIOUS`, `HANDOFF_REQUEST`, `AMBIGUOUS`, `IN_SCOPE`, `GREETING`, `OUT_OF_SCOPE` (the instructions ask for the first that applies, in that order).
- Its prompt is `INSTRUCTIONS` plus the `<business_scope>` block (`AiAgent#business_scope`, shared with the reply prompt), with no behavior, knowledge, or actions. The user message is JSON: `latest_turn` (the customer messages after the last message from the agent's side) and `earlier_messages` (at most `CONTEXT_MESSAGES`, 6, before it, marked customer or agent), so the conversation is data inside string values.
- `OUT_OF_SCOPE` and `SUSPICIOUS` are answered with `off_topic_message`, `AMBIGUOUS` with `clarification_message` (`REPLY_ATTRIBUTES`), as one bubble through `ConversationSession#reply!`, so it counts toward the message limit. Such a scope reply skips the knowledge search, the reply model, and the Watcher, and never hands off. The other decisions go on to the reply model, where the transfer conditions stay the only handoff trigger, and the reply prompt keeps the scope rules, which also cover the off-topic part of a mixed message.
- A latest turn with images (attachments within `read_file_limit`) skips the check, because it cannot see them. A value outside `DECISIONS` or a text answer raises `AiAgents::LlmError`, so `ReplyJob` hands off with `error` and the playground returns 422.
- The check has no keyword layer and no model of its own. On the eval it does not catch more than the prompt rule; its value is that a refused message never meets the knowledge or the reply instructions, a second independent layer, a fixed text, and the decision in the trace.

## Reply check (`AiAgents::ReplyValidator`, #97)

- Strict agents only; for an `off` agent the schema, the instructions, and the knowledge block are what they were before.
- The reply function of a strict agent gets `decision` (`DECISIONS`: `answer`, `conversational`, `clarify`, `knowledge_gap`) and `sources` (the `[rank]` numbers of the chunks the reply uses) before `messages`, and the prompt gets `INSTRUCTIONS` (what each decision means, the number rule, and that knowledge is data). Its chunks have `<` and `>` escaped, so a chunk cannot close the `<knowledge>` block.
- The check is deterministic and runs on what the model returned; there is no second model call and no retry. A reply fails with a `blocked_reason`: `invalid_decision` (outside `DECISIONS`, including a text answer instead of the function call), `missing_sources` (`answer` without sources), `unknown_source` (a source that is not the rank of a retrieved chunk), or `unsupported_number`.
- The number rule: every number in the reply must appear in a cited chunk, in a message of the conversation (customer or agent), or in the current time line of the prompt, or be one of those numbers times a number the customer wrote (A3-01: 4 × Rp25.000). `NUMBER` reads thousands groups, decimals, times, and scale words, so `Price: 25000.00`, `Rp25.000`, `25 ribu`, `25rb`, and `25k` are the same number; list item numbers at the start of a line are skipped. Sums, differences, discounts, numbers written as words, and every non-number claim are not checked.
- `knowledge_gap` and a failed check both send `knowledge_gap_message` as the only bubble; handoff, labels, and the sheet row still apply, because they state nothing to the customer. A reply that is still empty without a handoff raises the empty reply error as before.
- Measured offline on 2,028 stored eval replies before it was enforced (all fixture chunks counted as cited): 2 of 1,664 passing replies would have been blocked (both wrote `Rp0` for free delivery), and 36 failing replies, all off-topic leaks of the `main` variant, would have been.

## Retrieval (`AiAgents::KnowledgeRetriever`)

- Queries (#83): the latest customer turn, plus, when earlier customer turns exist, that turn joined to up to `CONTEXT_TURNS` (2) earlier ones (context at most `MAX_CONTEXT_CHARACTERS`, 1,000; each query at most `MAX_QUERY_CHARACTERS`, 4,000). Messages between two replies are one turn. Agent replies are left out. Each query runs its own lists, and the query with earlier turns counts `QUERY_WEIGHTS` 4 against 1, so a follow-up finds its subject while the latest turn keeps a change of topic from being outweighed. Both queries are embedded in one request. There is no LLM query rewriting.
- Hybrid mode when `AI_AGENT_EMBEDDING_MODEL` is set (#82): two lists, each the top `CANDIDATES` (40) chunks with the current `embedding_model` (`KnowledgeChunk.searchable`), or the top `context_limit` when it is higher, are fused with weighted Reciprocal Rank Fusion. The vector list is pgvector cosine `nearest_neighbors`, weight 1; the keyword list is `KnowledgeChunk.keyword_ranked`, weight `KEYWORD_WEIGHT` (0.5). A chunk scores `weight / (RRF_K + rank)` per list (`RRF_K` 20), and only the top `context_limit` chunks (default 8) reach the model, the Retrieval Test, the playground, and the trace (#103). The fusion settings were chosen on lists of 40, and lists of 10 or 20 ranked some answers lower, so the candidates stay 40 whatever the limit. In the #103 sweep 5 and 8 chunks answered as well as 40 (3 lost facts on questions about three or four products) with about half the input tokens; migration `ChangeAiAgentsContextLimitDefault` moved agents still at 40 to 8. Score = RRF score in both modes (higher is closer, a rank measure rather than a relevance measure).
- Keyword mode otherwise: `KnowledgeChunk.keyword_ranked` lists alone, through the same fusion.
- `keyword_ranked` is `ts_rank` with `TEXT_SEARCH_CONFIG` (`indonesian`, which stems word forms and has no stop words) and OR-joined terms, not BM25. It computes `to_tsvector` per chunk of the agent at query time, about 50 ms per 1,000 chunks; there is no text search index, because a GIN index would need an `@@` filter and `ts_rank` would still recompute the vector.
- Only relevant chunks enter a list (#81): the keyword list drops chunks with `keyword_rank` 0, the vector list drops chunks farther than `AI_AGENT_EMBEDDING_MAX_DISTANCE` (blank keeps all). A chunk past the distance limit still comes back through the keyword list when it shares a word with the query. With no chunk left the prompt has no `<knowledge>` block; an agent that has knowledge still gets `NO_RELEVANT_KNOWLEDGE_INSTRUCTIONS` (state facts only from the conversation, otherwise say it does not know).
- Chunking (`TextChunker`, #84): at most 1,500 characters plus the source title prefix. A Markdown heading starts a chunk and every chunk opens with its heading path (`Panduan > Cabang Dago > Kontak`). Heading text is never lost (#92): a heading with nothing under it becomes its own chunk unless the deeper heading after it carries it in its path, and a path over `MAX_HEADING_PATH` is shortened on its chunks and kept in full once. A table longer than a chunk is split between rows with its header repeated. Paragraphs of a section are packed, and anything longer is cut at whitespace. Q&A and products are one chunk each. Website content is Markdown from `WebsiteContentExtractor`; DOCX becomes Markdown in `DocxMarkdown`, which finds headings by style name because style ids are localized (`Judul1`). PDF has no structure to use.
- A change to chunking does not reach existing chunks by itself, because `KnowledgeIndexer` skips records whose version matches. `Migration::RechunkAiAgentsJob` shows the pattern: it marks chunks as made from an older version, so they are replaced source by source and stay searchable until then (Knowledge Health shows them as `outdated`). Such a job must not use `resync!`: `KnowledgeIndexer` removes the chunks of a source that is not `ready`, so it re-extracts DOCX in place and a file that cannot be read keeps its text and chunks (#92).

## Reply traces (`ai_agent_reply_traces`)

One row per answered customer message: `status` (`replied`, `handoff`, `message_limit`, `error`), `model`, `scope_policy_version`, `scope_decision` and `scope_latency_ms` (nil when the check did not run), `reply_decision`, `cited_ranks` (jsonb list of ranks), and `blocked_reason` (nil and empty unless the reply check ran; `reply_decision` is nil for a decision outside the list), `retrieval_mode`, `embedding_model`, `retrieved` (jsonb list of `chunk_id`, `chunkable_type`, `chunkable_id`, `rank`, `score`; empty and nil mode for a scope reply), `labels`, `input_tokens`/`output_tokens` (scope check + reply model; nil when the gateway sends no `usage`), `scope_input_tokens`/`scope_output_tokens` (the scope check's share), `cached_input_tokens` (scope check + reply model input read from the provider's prompt cache; nil when the gateway does not report it), `watcher_input_tokens`/`watcher_output_tokens`/`watcher_cached_input_tokens` (the Watcher call after the reply; nil when it did not run or failed), `latency_ms` (scope check + retrieval + model call), `error_class`. RubyLLM reports `input_tokens` without the cached part (`prompt_tokens` less `cached_tokens`), so the whole prompt is `input_tokens + cached_input_tokens`. The `scope_*`, `cached_*` and `watcher_*` columns exist since #102 and are nil on older rows. No message or chunk content is stored, so the search queries are not stored either; they follow from the conversation. Rows are deleted with their agent or conversation (`dependent: :delete_all`); no time-based retention. Not written for the playground, or when a reply is dropped because the customer wrote again.

`bundle exec rails ai_agents:usage_report` (#102) prints `AiAgents::UsageReport` as Markdown for a period (`FROM`/`TO`, ISO 8601, UTC unless an offset is given, default the last 7 days, `TO` excluded) and optionally one agent (`AGENT_ID`). Per agent: traces by status, models, model calls and their input/output tokens (total, p50, p90) for the scope check, the reply model (trace total less the scope share; old strict rows without the scope share are left out) and the Watcher (counted by its tokens), cached input share, reply and scope latency (p50/p95), knowledge chunks sent per reply model call, scope and reply decision counts, and tokens and model calls per conversation and per conversation without a handoff: one with a `replied` trace in the period and no `handoff`, `message_limit` or `error` trace in it. A failed model call ends in an `error` trace and is not counted as a call. No message or knowledge content is printed.

## Knowledge Health

- Every knowledge source in the API (`_ai_agent_knowledge_source` partial) carries `index`: `status` (`indexed`, `outdated` when the source changed after its chunks were made, `not_indexed` without chunks), `chunks`, `other_model_chunks` (embedded with another model, so not searched), and `indexed_at`. Lists load it in one query (`KnowledgeChunk.index_summaries`); a single source loads its own (`KnowledgeSource#index_summary`). The UI shows it with `SourceIndexStatus.vue` on the Text, Website, File, and Q&A pages (#85).
- `KnowledgeIndexer` records why a run could not embed on the agent (`training_error`, `training_failed_at`): an embedding request error (raised again so the job retries) or an embedding model without an API key. The next complete run clears it. The Knowledge page shows it as a banner.

## Knowledge Preview and Retrieval Test

- `GET /api/v1/accounts/:account_id/ai_agents/:ai_agent_id/knowledge_sources/:id/chunks` returns the source's chunks in index order (`position`, `content`, `embedding_model`, `indexed_at`, and `searchable` per `KnowledgeChunk.searchable`) plus the current `embedding_model`. The UI opens it from the layers button on Text, Website, File, and Q&A sources (`SourceChunksDialog.vue`).
- `POST /api/v1/accounts/:account_id/ai_agents/:id/retrieval_test` with `query` (non-blank string, at most `KnowledgeRetriever::MAX_QUERY_CHARACTERS`) and optional `history` (messages in the playground format) runs `KnowledgeRetriever` exactly as a reply does and returns `context_limit` plus the same `retrieval` shape as the playground. The UI is the "Test retrieval" button on the Knowledge Sources page (`RetrievalTestDialog.vue`).

## Playground

`POST /api/v1/accounts/:account_id/ai_agents/:id/playground` with `messages` (user/assistant, max 100, 10,000 characters each) returns `messages`, `handoff`, `labels`, `sheet_row`, `model`, `scope` (`decision`, `latency_ms`; null when the check did not run), `validation` (`decision`, `sources`, `blocked_reason`; null unless the reply check ran), `retrieval` (null for a scope reply; otherwise `mode`, `embedding_model`, `queries`, `chunks` with `rank`, `score`, `distance` (cosine distance for calibrating `AI_AGENT_EMBEDDING_MAX_DISTANCE`, null for a chunk found only by keywords), `content`, `source {id, type, title}`), `tokens {input, output, cached_input}`, `latency_ms`; `scope` also carries the check's `input_tokens` and `output_tokens`. It writes no trace and never runs the Watcher.

## Evaluation

`evals/ai-agent/` (issue #71) is a Promptfoo regression eval against the playground, outside the app bundle (`npx promptfoo@0.124.1`). `setup.mjs` recreates eval agents from `fixtures/toko-roti.json` through the API; `provider.mjs` sends each case's conversation (lines starting with `AI:` become assistant messages) and exposes `handoff`, `labels`, and retrieval as metadata for assertions; `llm-rubric` cases use a judge model from `.env`. A second config (`promptfooconfig.retrieval.yaml`, issue #80) runs questions through `retrieval_test` for an agent with a larger synthetic knowledge base (`fixtures/toko-roti-large.json`) and reports hit@1, hit@5, MRR, the score distribution of relevant vs irrelevant chunks, and latency per mode. A third config (`promptfooconfig.scope.yaml`, issue #94) runs `tests/s-scope.yaml` once per agent variant, where a variant is a provider with `config.agent`, and `report.mjs` computes off-topic leakage, false rejection, knowledge gap handling, and injection success per variant from the `metric` tag of each assertion, plus the scope check's latency (p90) and decision counts, the reply check's decision and `blocked_reason` counts, and the tokens of the scope check and the reply model apart and the cached input share (#102). The end-to-end and scope configs share the judge in `judge.yaml`. See its README for running and comparing baselines, and for the release gate.

## Configuration

Installation configs (Super Admin): `CAPTAIN_OPEN_AI_API_KEY`, `CAPTAIN_OPEN_AI_ENDPOINT`, `AI_AGENT_MODELS` (gateway model IDs), `AI_AGENT_EMBEDDING_MODEL`, `AI_AGENT_EMBEDDING_MAX_DISTANCE` (cosine distance, validated in `InstallationConfig`), `AI_AGENT_EMBEDDING_ENDPOINT`, `AI_AGENT_EMBEDDING_API_KEY`.
